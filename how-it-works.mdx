Scramjet proxies web content entirely within the browser by combining four cooperating layers: a Service Worker that intercepts every network request, a Controller that coordinates fetch dispatch from the host page, a Rust/WASM rewriter that transforms HTML, CSS, JavaScript, and WebAssembly, and a transport layer that tunnels proxied requests to the upstream server over WebSockets. No browser extension, no native code, and no modification to the proxied site's source code is required.

## The Four Layers

```
┌──────────────────────────────────────────────┐
│  Host Page (your app)                        │
│  ┌────────────┐   MessageChannel   ┌───────┐ │
│  │ Controller │◄──────────────────►│  SW   │ │
│  │  + Frame   │                    └───┬───┘ │
│  └────────────┘                        │     │
│        │                          intercepts │
│        ▼                          all fetch  │
│  ┌───────────┐                        │     │
│  │ Transport │◄───────────────────────┘     │
│  │(libcurl / │  RPC: request / connect      │
│  │  epoxy)   │                              │
│  └─────┬─────┘                              │
│        │ Wisp WebSocket                     │
└────────┼───────────────────────────────────-┘
         ▼
   Node.js Server  ──► Internet
```

### Layer 1 — Service Worker

The Service Worker (SW) is the front door of the proxy. It is registered from `sw.js` (generated by `proxy-bootstrap`) and runs in a separate global scope from the host page. Its only job is to intercept `fetch` events:

```js
// Generated sw.js
importScripts("/controller/controller.sw.js");
addEventListener("fetch", (e) => {
  if ($scramjetController.shouldRoute(e)) {
    e.respondWith($scramjetController.route(e));
  }
});
```

`shouldRoute` returns `true` for any request whose URL pathname starts with the controller's proxy prefix — for example `/~/sj/abc123def/xyz789/`. All other requests pass through to the network normally, so your host-page assets load without interference.

When the SW needs to fulfil a proxied request, it does **not** make the upstream HTTP request itself. Instead it passes the request metadata to the `Controller` via a private `MessageChannel` RPC and waits for the Controller to return the response body.

### Layer 2 — Controller and Frame

The `Controller` class runs on the host page. It is responsible for:

- Opening and maintaining a `MessageChannel` to the SW (re-establishing it automatically if the SW is revived after being killed).
- Holding the transport instance (`ProxyTransport`) that makes real outbound network requests.
- Maintaining the `CookieJar` for all proxied origins, persisting it to **IndexedDB**, and syncing changes across tabs via `BroadcastChannel`.
- Loading the Rust/WASM binary once and making it available to the rewriter.

```ts
const controller = new Controller({
  serviceworker: sw,          // the registered ServiceWorker object
  transport: myTransport,     // epoxy or libcurl transport instance
});

await controller.wait();      // resolves when SW handshake and WASM load are complete
```

A `Frame` wraps a single `<iframe>` element and owns a `ScramjetFetchHandler` instance. When the SW dispatches a `request` RPC call, the Controller routes it to the correct Frame based on which prefix the request URL falls under, and the Frame's fetch handler processes it.

```ts
const frame = controller.createFrame(iframeElement, { plugins: [...] });
frame.go("https://example.com");   // encodes the URL and sets iframe.src
frame.back();                      // calls contentWindow.history.back()
frame.reload();                    // calls contentWindow.location.reload()
```

Each Controller gets a random ID (`makeId()` — 8 base-36 characters), and each Frame gets its own random ID, yielding unique per-frame path prefixes: `/~/sj/{controllerId}/{frameId}/`.

### Layer 3 — Rust/WASM Rewriter

The rewriter is a WebAssembly module compiled from Rust that performs AST-level transformation of JavaScript. It is loaded once per controller via a `fetch` of `scramjet.wasm` and then shared across all frames.

<Note>
  The WASM binary is **not** built automatically when you install the npm package in a typical deployment — `proxy-bootstrap` downloads the pre-built binary from the npm registry. If you are building Scramjet from source you must run `pnpm rewriter:build` inside `packages/core`, which requires `rustup`, `wasm-bindgen`, Binaryen's `wasm-opt`, and a fork of `wasm-snip`.
</Note>

The rewriter handles four content types:

<Tabs>
  <Tab title="JavaScript">
    JavaScript is rewritten at the **AST level** using OXC (a fast Rust-based JS parser). The rewriter wraps property accesses and assignments that could read or leak the proxied page's real origin. For example, a script that reads `window.location` is rewritten to call `$scramjet$wrap(window).location` instead, and the runtime shim returns the *proxied* URL rather than the real one.

    Key rewriter globals injected into every proxied JavaScript context:

    | Global | Purpose |
    |---|---|
    | `$scramjet$wrap(target)` | Wraps an object so property accesses are intercepted |
    | `$scramjet$prop(key)` | Maps a property name to its intercepted alias (e.g. `"location"` → `"$scramjet__location"`) for computed property accesses |
    | `$scramjet$rewrite(js)` | Rewrites a JS string for direct `eval()` calls so the evaluated code is proxied |
    | `$scramjet$meta` | Rewrites `import.meta` accesses, supplying the proxied `url` and a `resolve()` function |
    | `$scramjet$import(base, url)` | Rewrites dynamic `import()` calls by resolving `url` against `base` and encoding it |
    | `$scramjet$clean(restid)` | Cleans up rest-spread destructure temporaries that may contain intercepted property names |

    Source maps can be generated and stored (controlled by the `sourcemaps` flag) so that browser DevTools show original line numbers.
  </Tab>
  <Tab title="HTML">
    HTML is parsed with `htmlparser2`. For each element, the rewriter walks `htmlRules` — a table mapping tag/attribute pairs to rewrite handlers. Attributes that contain URLs (e.g. `href`, `src`, `action`, `srcset`) are encoded via the proxy codec. Inline `<script>` bodies are passed through the JS rewriter. Inline `<style>` bodies and `style=""` attributes are passed through the CSS rewriter.

    Before the closing `</head>` (or at the top of `<body>` if there is no `<head>`), the rewriter injects a block of `<script>` tags that:
    1. Load the Scramjet JS bundle.
    2. Load the WASM binary (as a virtual JS file that sets `self.WASM`).
    3. Load the controller inject script.
    4. Call `$scramjetController.load(...)` with the serialised config, cookie jar, codec functions, and history state.
  </Tab>
  <Tab title="CSS">
    CSS is processed with a lightweight streaming rewriter. Every `url(...)` value found in stylesheets or inline `style` attributes is passed through the proxy codec so that image, font, and background-image references resolve correctly through the proxy.
  </Tab>
  <Tab title="WebAssembly">
    WebAssembly binaries are inspected for imported functions that match known browser globals (such as those that could return or expose the real page origin). Matching imports are patched so that calls route through Scramjet's interception shims instead of directly to the browser API.
  </Tab>
</Tabs>

### Layer 4 — Transport

The transport layer is responsible for making the actual upstream HTTP and WebSocket connections. All traffic is tunnelled over a **Wisp** WebSocket connection from the browser to the Node.js server, which then forwards requests to the public internet.

Two transport implementations are supported:

<CardGroup cols={2}>
  <Card title="libcurl (default)" icon="globe">
    `@mercuryworkshop/libcurl-transport` — a WASM build of libcurl. Selected with `transport: 'libcurl'` in `bootstrap()`. Broad protocol support; the default for new projects.
  </Card>
  <Card title="epoxy" icon="bolt">
    `@mercuryworkshop/epoxy-transport` — an alternative WASM transport. Selected with `transport: 'epoxy'` in `bootstrap()`. Different performance and compatibility tradeoffs from libcurl.
  </Card>
</CardGroup>

The transport interface is pluggable — you can supply any object that implements `ProxyTransport` (from `@mercuryworkshop/proxy-transports`) when constructing a `Controller`.

## URL Encoding

Every proxied URL is encoded and embedded inside a path that begins with the proxy prefix. The default codec uses `encodeURIComponent` / `decodeURIComponent`:

```
Original:   https://example.com/path?q=1
Proxied:    /~/sj/{controllerId}/{frameId}/https%3A%2F%2Fexample.com%2Fpath%3Fq%3D1
```

The codec is fully configurable. Pass `encode` and `decode` functions to `ScramjetInitConfig.codec` to use a different encoding scheme (e.g. Base64, XOR, or a custom obfuscation layer).

The `rewriteUrl` utility (exported from `@mercuryworkshop/scramjet`) is used throughout the rewriters to consistently encode URLs, taking into account the current page's base URL for resolving relative paths before encoding.

## Cookie Sandboxing

Scramjet fully sandboxes cookies away from the host page's cookie storage. Instead of writing to `document.cookie`, the proxied runtime uses a `CookieJar` instance maintained in the `Controller`:

```
Proxied page           Controller (host page)         IndexedDB
──────────             ──────────────────────         ─────────
Set-Cookie header  ──► cookieJar.setCookies()     ──► writeCookieState()
document.cookie    ──► cookieJar.getCookies()     ◄── readCookieState()
                       persistCookies()
                       BroadcastChannel ──► other tabs sync
```

1. When the transport receives a `Set-Cookie` response header, it calls `sendSetCookie` on the Controller via RPC.
2. The Controller updates the in-memory `CookieJar` and writes the serialised state to IndexedDB.
3. A `BroadcastChannel` message is posted so other tabs running the same Controller ID can sync their cookie state immediately.
4. On the next request, `loadSavedCookies()` reads from IndexedDB and applies any updates before the request is dispatched.

This means cookies are never visible in DevTools' "Application → Cookies" panel and cannot be accessed by the host page's own JavaScript.

## Configuration Flags

`ScramjetConfig.flags` controls the behaviour of the rewriter and runtime. All flags are set at `Controller` construction time and can be overridden per site via `siteFlags`.

| Flag | Default | Description |
|---|---|---|
| `sourcemaps` | `true` | Generate and store source maps for rewritten JS so DevTools shows original code |
| `syncxhr` | `false` | Enable synchronous `XMLHttpRequest` support (requires `SharedArrayBuffer`) |
| `captureErrors` | `false` | Catch and report rewriter errors instead of letting them propagate |
| `cleanErrors` | `false` | Strip Scramjet stack frames from errors shown to proxied pages |
| `rewriterLogs` | `false` | Log timing information for each rewriter invocation to the console |
| `disableComputedWrap` | `false` | Skip wrapping computed property accesses (faster but less compatible) |
| `scramitize` | `false` | Enable extra obfuscation of rewritten globals |
| `destructureRewrites` | `true` | Rewrite destructuring assignments that could expose intercepted properties |
| `allowInvalidJs` | `true` | Continue rewriting even if the input JS does not parse cleanly |
| `allowFailedIntercepts` | `false` | Let intercepted property accesses fall through if the shim throws |
| `encapsulateWorkers` | `true` | Inject the Scramjet runtime into `Worker` and `SharedWorker` contexts |
| `debugTrampolines` | `false` | Insert extra assertions in generated trampoline code (dev only) |
| `debugSourceURL` | `false` | Append `//# sourceURL` comments to rewritten scripts (dev only) |

<Tip>
  The package exports a `defaultConfigDev` preset that enables `captureErrors`, `debugTrampolines`, and `debugSourceURL` while disabling `allowInvalidJs`. Use it during development to get better error messages and source-map integration.
</Tip>

## Request Flow Diagram

The following steps trace a single `fetch("https://api.example.com/data")` call made by JavaScript running inside a proxied page.

<Steps>
  <Step title="JS Makes a fetch Call">
    The proxied script calls `fetch("https://api.example.com/data")`. The Scramjet runtime has replaced the native `fetch` with a shim that encodes the URL and re-issues the request through the proxy prefix: `fetch("/~/sj/abc/xyz/https%3A%2F%2Fapi.example.com%2Fdata")`.
  </Step>
  <Step title="Service Worker Intercepts">
    The SW's `fetch` listener fires. `shouldRoute` matches the prefix and `$scramjetController.route(event)` is called, which serialises the request (URL, method, headers, body, destination, referrer) and sends it to the Controller via `MessageChannel` RPC.
  </Step>
  <Step title="Controller Dispatches">
    The Controller receives the `request` RPC call, looks up which `Frame` owns that prefix, waits for cookies to be loaded from IndexedDB, then calls `frame.fetchHandler.handleFetch(...)`.
  </Step>
  <Step title="Transport Fetches Upstream">
    The fetch handler calls `transport.request(new URL("https://api.example.com/data"), ...)`. The transport tunnels this over the Wisp WebSocket to the Node.js server, which makes the real HTTP request and streams the response back.
  </Step>
  <Step title="Response Rewriting">
    The response body is passed through the appropriate rewriter (JSON and most API responses pass through unmodified; HTML, JS, CSS, and WASM are rewritten). Any `Set-Cookie` headers are extracted, sent to the `CookieJar`, and stripped from the response before it reaches the page.
  </Step>
  <Step title="Response Returned">
    The rewritten (or unmodified) response is serialised and sent back to the SW via RPC. The SW calls `event.respondWith()` with the response, and the browser resolves the original `fetch()` promise inside the proxied page.
  </Step>
</Steps>
